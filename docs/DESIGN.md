# 有界缓冲下的多租户安全批次发布

原生 Windows + Python 3.12 标准库实现。输入为本地合成回执流，验证全部在本地完成。

## 1. 目标与约束

- **受限暂存**：所有工作内存在一个 8 MiB 硬上限下，按五个**独立计数**的池核算：压缩输入、解压区、索引排队、待确认页、重试仍持有的缓冲。五池之和即真实常驻工作集，超过即失败，不会静默膨胀。
- **按租户发布**：每个租户、每个批次独立目录；一个批次只有在其 `COMMIT` 指针持久化后才算**已批准**，才会出现在索引、通知和对外读口。
- **可重复恢复**：恢复只凭磁盘状态即可重建“哪些批次已批准”，且重复执行结果一致（幂等）。
- **失败不可见**：末页摘要错误、目录已刷但指针未刷、线程中止等失败，批次从索引、通知、读口三处都不可见，磁盘残留被回收。

## 2. 两个输入线程与合并

每个批次由两个生产者线程提供分页。两个线程在**重叠窗口**内会携带相同序号：

- 相同序号 + 相同内容 → 合并（`duplicates_merged` 计数），只保留一份。
- 相同序号 + 不同内容 → 冲突，整批失败（不允许有歧义的页进入已批准集合）。

页在线上是 zlib 压缩的；接收端按序解码到解压区。

## 3. 提交协议（目录已刷、指针未刷）

批次目录内：`segment.bin`（所有页按序分帧、带逐页摘要）+ `COMMIT`（批准指针）。

```
写 segment.bin 全部字节，fsync(segment)
fsync(批次目录)                 ← segment 文件名持久
   ── 在此崩溃：segment 持久、无指针 ⇒ 未批准 ──
写 COMMIT.tmp，fsync(COMMIT.tmp)
   ── 在此崩溃：指针内容持久、指针名不存在 ⇒ 未批准 ──
rename COMMIT.tmp -> COMMIT
   ── 在此崩溃：重命名是否持久不确定；恢复看到旧（无 COMMIT⇒未批准）
      或新（COMMIT⇒已批准），两者都一致 ──
fsync(批次目录)                 ← COMMIT 文件名持久 ⇒ 已批准
```

“目录已刷但指针未刷”正是第一次与最后一次目录 fsync 之间崩溃：segment 已持久但无指针，恢复必须丢弃。

指针是**唯一**的批准来源。恢复时会再次校验：段前缀长度与 SHA-256、逐页长度与摘要、末页确为摘要页、内容摘要等于指针记录、页偏移恰好铺满段前缀、页序严格递增。任一不满足 ⇒ 删除该批次目录。段前缀之后被追加的字节是未批准的尾巴，恢复时截断丢弃，从不读取。

Windows 上目录 fsync 需要 `FILE_FLAG_BACKUP_SEMANTICS` 且**必须带写访问**，只读句柄会返回 `ERROR_ACCESS_DENIED`；`durability.fsync_dir` 依次尝试读写/列目录/只写三种访问掩码。另外 Windows 的 `os.open` 默认**文本模式**会把 `0x0A` 翻译成 `0x0D0A` 破坏二进制段，因此所有底层打开都强制 `O_BINARY`。

## 4. 末页摘要

末页携带 `(magic, 页数, 覆盖此前所有页的 SHA-256)`。校验发生在**前面所有页都已读入并暂存之后**：摘要不符 ⇒ 整批失败，前面读过的页一并丢弃。这样“最后才失败”不会泄漏任何已读数据。

## 5. 缓冲预算与回收时机

`Budget` 是一把锁下的字节账本：一个全局硬上限 + 五个独立计数池，支持多池**原子**预占（要么全拿到要么一点不占）、超上限请求**立即可失败**（不会永久阻塞）、峰值高水位追踪。`transfer` 在同一次移动中把同一份字节从一个池挪到另一个池，不改变总量。

每页按 `len(payload) + 160` 字节计费：160 是 CPython 3.12 上每页 Python 对象开销的实测上界（dict 槽、`bytearray` 头、整型键，实测约 121 B/页，取 160 留余量）。因此账本反映的是**真实常驻内存**，而不是只数 payload 的下界。

| 池 | 何时计费 | 何时归零 |
|---|---|---|
| COMPRESSED | 读入一页的压缩字节时 | 该页解压完成的瞬间（逐页，不累积） |
| ARENA | 按 ≤chunk 步进随解码增长计费 | 页解压并移交批次后归零；空闲 chunk 立即退回 |
| PENDING_PAGES | 解压后的页在批次校验前持有 | 批次校验后**移动**（非释放）到下一池 |
| INDEX_QUEUE | 已校验批次在索引/提交期间持有 | `COMMIT` 指针持久且发布到索引后释放 |
| RETRY_HELD | 瞬时提交失败及其退避期间持有 | 重试后移回 INDEX_QUEUE；最终提交或失败后归零 |

解压使用**增量有界**方式：每次只预占一个 chunk，解出一个 `bytearray` 并原地增长（不二次拷贝），空闲 chunk 立即退回；单页超过 `max_page_uncompressed` 直接拒绝，而不是先分配大缓冲。因此一个“谎报大小”的页也无法冲破预算。

两个生产者可以**同时**各持有一份压缩页和一个解压 chunk，预算把它们分别独立计数——这正是“最坏交错”。

## 6. 故障注入与恢复证明

- **末页摘要错误**：`BatchStream(summary_corrupt=True)` 翻转末页首字节 → 整批失败，索引/通知/读口均无，磁盘目录被删，预算归零。
- **目录已刷指针未刷**：`CommitHooks({"after_segment_dir_fsync": raise})` → 重启后 `recover()` 判定未批准并删除，兄弟已批准批次仍可读。
- **线程中止**：`abort_kind="abort"` 抛 `ThreadAborted`，批次失败但进程继续，其他租户/批次继续可读。
- **进程崩溃**：`abort_kind="crash"` 抛 `CrashInjected`，主线程向上传播；新建 `Receiver` 调用 `rebuild_from_store()` 后，仅已批准批次可见。

恢复后**其他租户能继续**：每租户独立目录，恢复逐租户进行，某个租户的坏批次不影响其他租户。**不会读取未批准数据**：读口先查内存索引（只含已发布批次），再让 store 重新校验页字节；未批准批次即便磁盘残留也不会被读出。

## 7. 十万条实测

见 `bench/reports/bench_100k.json`（由 `python -m bench.run_benchmark 100000` 生成，`tests/test_full_100k.py` 复现）。配置：100,000 条、每批 13,000 页、每页 384 字节 payload、每页计费 544 字节。实测：

| 指标 | 数值 |
|---|---|
| 账本总峰值 | 7,270,055 B ≈ **86.7% of 8 MiB** |
| tracemalloc 实测进程峰值 | 7,889,285 B ≈ **94.1% of 8 MiB**（真实分配也在上限内） |
| 每池峰值 | COMPRESSED 53 B、ARENA 32 KiB、PENDING/INDEX 各 7.27 MB、RETRY_HELD 0 |
| 吞吐 | ~6,700 页/秒（含每次提交的多道 fsync） |
| 合并的重复页 | 576（重叠窗口） |
| 超预算批次检查 | 8.65 MB 计费 > 8.39 MB 上限 ⇒ **拒绝**，账本归零 |

**最坏交错**：两个生产者在重叠窗口内同时持有同一序号；最繁忙池为 INDEX_QUEUE，峰值出现在整批校验后、提交前。两个生产者并发持有上界为压缩页 ×2 与解压 chunk ×2（合计约 33 KB），远小于整批 7.27 MB——即真正的峰值由“整批已校验待提交”决定，而非逐页缓冲。

规模测试（`tests/test_benchmark.py`）在 CI 中以缩小规模覆盖同一路径，并断言 ARENA/COMPRESSED 的峰值**不随批次规模增长**（逐页/逐 chunk 有界），而 INDEX_QUEUE 才是整批有界。
